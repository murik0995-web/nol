# ТЗ «Волна 1: надёжность Завода» (эпика WAVE1)

Документ для агентов конвейера. Читай весь документ перед первой правкой, потом только свой раздел 3.x. Источник задачи: `factory/PLAN-2.md`, раздел 2. Если код разошёлся с этим текстом, побеждает код; расхождение опиши в журнале событием `build`.

## 0. Зачем

Завод конвейера построил NOL за три недели, но обкатка вскрыла пять слабых мест в самом демоне (`factory/daemon/conveyor.mjs`) и два в приложениях: гейты глушат HTTP-сервер на минуты; лимит подписки останавливает завод на часы без предупреждения; убитый по таймауту заход теряет всю работу; повторно взятая карточка не сбрасывает модель; самотест демона может быть красным и никто не узнает; приложения живут только на демо-данных без пути с настоящей выгрузкой; localStorage упрётся в потолок на первой настоящей базе. Эта волна чинит все семь.

## 1. Инварианты

1. Каждая карточка = один агент = один коммит, как в эпике ZAVOD.
2. `node factory/daemon/selftest.mjs` зелёный после каждой правки `factory/daemon/*.mjs`; `node --test`, `node scripts/build.mjs`, `node scripts/smoke.mjs` зелёные всегда.
3. Существующее поведение демона не ломать: форма ответов `/api/state`, `/api/usage`, `/api/epics`, `/api/task/:id/*` не меняется, только расширяется.
4. Правила `factory/CONVENTIONS.md` действуют: `NOL.h`, `NOL.val`, русский словарь на каждую новую строку, никаких зависимостей и сборки.
5. Ничего не спрашивай владельца об этом документе. Вопрос — только о поведении продукта, которого здесь нет, или об удалении данных.
6. Пять карточек этой волны (1.1–1.5) правят один и тот же файл `factory/daemon/conveyor.mjs`. Порядок строгий, следующая карточка не начинается, пока предыдущая не влита в main — так же, как в ZAVOD.

## 2. Общее по коду (проверено 24.09, коммит fdd9048)

- `shell(cmd, cwd, timeout)` в `factory/daemon/conveyor.mjs:1632` вызывает `execFileSync` — синхронно, блокирует единственный поток Node на всё время команды. Пять точек вызова циклом `for (const cmd of repo.cfg.validation) { const r = shell(cmd, wt) }`: строки 488 (откат), 1615 (`validate`), 1835 (`mergeTask` после rebase), 1891 (`finalizeEpic`), 1986 (`nightly`). Все пять — внутри уже `async`-функций конвейерного пайплайна.
- `AGENT_TIMEOUT_MS` (строка 21) = 45 минут по умолчанию, читается как `repo.cfg.timeout_min` в `runAgent` (строка 1507), таймер строка 1509–1511: `kill('SIGTERM')`, потом `SIGKILL` через 10 секунд.
- `runVariant` (около строки 2060) уже умеет продолжать существующий воркспейс: `opts.resume` (id сессии) + `task.worktree` — тогда пропускает `prepare()` и `setup`, зовёт `runAgent(..., {resume: opts.resume})`. Это тот же механизм, что слово владельца (`ownerSays`) использует для «доработки» без потери контекста.
- `run('UPDATE runs SET ..., session=? WHERE id=?', ...)` (строка 1521) пишет id сессии из последней строки stdout при завершении процесса ПО СОБЫТИЮ `close`. При убийстве по таймауту процесс тоже даёт `close`, значит session туда уже попадает, если stdout успел донести `session_id` (он приходит в первой строке `system/init`, а не в последней — session известен с самого начала работы).
- `fail(task, reason)` (строка 2026): при `!noRetry && attempts < MAX_ATTEMPTS` повторяет тем же или следующим потолком модели (репо-пин уважается, чинено 23.09) и ставит `status='queued'`. `MAX_ATTEMPTS = 2`.
- `nolSync` (строка ~432–452): для карточки, снова поставленной в Queued с существующей записью `status IN ('cancelled','failed')`, делает `UPDATE tasks SET attempts=0, error=NULL` и `setStatus('queued')` — но НЕ трогает `model`. Старая модель (например `opus` от эскалации до провала) переживает возврат в очередь. Обнаружено вживую 23.09: пришлось руками сбрасывать `model` дважды.
- Перезапуск демона (строка 2828, `reapOrphans`-соседний код) для «подвисших» задач делает `attempts = MAX(attempts-1, 0)` — это разумно и трогать не нужно; проблема именно в `model`, не в счётчике попыток.
- `daemon-check.mjs` вызывается из `conveyor.json`'s `validation` как `test -f scripts/daemon-check.mjs && node scripts/daemon-check.mjs || true` — `|| true` глушит любой красный результат. Ни один workflow в `.github/workflows/` не гоняет `factory/daemon/selftest.mjs`.
- NOL.store (`assets/nol.js`, функции `load()/persist()` около строки 10) держит всю базу приложения (`db`) целиком в одном ключе `localStorage`. Отдельно там же в localStorage: язык (`LANG_KEY`), настройки синка (`SYNC_KEY`), недавние результаты поиска (`RECENT_KEY`), «показано»-метки (`kept/keep`). Трогаем только `db` — это единственное, что растёт без предсказуемого потолка.
- `NOL.store.importAll(json)` (строка 29) читает только собственный экспорт NOL (`{coll: [...]}`), это не про импорт из внешних систем.

## 3. Карточки. Порядок строгий для 3.1–3.5, 3.6–3.7 можно в любой момент после них

### 3.1 W1-1 · Гейты не блокируют демон
Файл: `factory/daemon/conveyor.mjs`, `factory/daemon/selftest.mjs`.
Перепиши `shell()` на асинхронный вариант поверх `spawn` (не `execFileSync`): собирай stdout/stderr в буфер, таймаут через `setTimeout` + `kill`, верни ту же форму `{code, out, killed}`, что и сейчас — чтобы вызывающий код (пять точек из раздела 2) не пришлось трогать сверх добавления `await`. Замени `shell(cmd, wt)` на `await shell(cmd, wt)` во всех пяти точках; проверь, что каждая объемлющая функция действительно `async` (validate, revertTask, mergeTask, finalizeEpic, nightly) — если какая-то нет, сделай её `async` и поправь её вызывающих тем же способом вверх по цепочке, пока не дойдёшь до точки, которая уже `await`-ится.
Приёмка: во время `node scripts/smoke.mjs` (реально идущего через гейт `validate`) параллельный `curl localhost:7777/api/state` отвечает быстрее секунды — добавь этот сценарий в `selftest.mjs`: запусти долгую фиктивную команду в `validation` и одновременно дёрни `/api/state`, замерь время ответа, провалить самотест если больше 1 секунды. Существующие пять сценариев самотеста остаются зелёными.

### 3.2 W1-2 · Квота как планировщик
Файл: `factory/daemon/conveyor.mjs`.
Перед тем как `nextTask()` отдаёт задачу в работу (там, где сейчас решается модель через `intake`/`pickModel`), спроси `usage()` (уже существующая функция для `/api/usage`, кэш 60 секунд). Если `limits[].percent` для активного окна (`kind='session'`) больше 80 — не бери новую задачу с оценкой стоимости (`estimate`) выше медианной по репозиторию, дай отработать дешёвым; если больше 95 — не бери вообще, кроме задач с `priority=1` (срочных). Если `weekly_all.percent` больше 90 и известен `resets_at` в пределах суток — залогируй событием `квота` время следующего разумного окна, ничего больше не меняй в логике (не планируй расписание — это отдельная задача, если понадобится).
Приёмка: селфтест-сценарий с фиктивным `usage()` под 95% и задачей `priority=0` — задача не стартует, событие `квота` пишется; с `priority=1` — стартует.

### 3.3 W1-3 · Продолжение вместо перезапуска
Файл: `factory/daemon/conveyor.mjs`.
Сейчас таймаут (раздел 2, `AGENT_TIMEOUT_MS`/`timeoutMs`) шлёт `SIGTERM`→`SIGKILL`, `close`-обработчик видит `exit_code=143` и это уходит в `fail()` как обычный провал — воркспейс с несохранённым диффом теряется при следующей чистой попытке (`prepare()` пересоздаёт worktree с нуля). Почини: в обработчике таймера (строки 1509–1511) НЕ убивай сразу — сначала попробуй мягко: если `git(wt, 'status', '--porcelain')` не пуст, сделай `git add -A && git commit -m "WIP: таймаут захода, продолжение в следующей попытке"` В ТОМ ЖЕ воркспейсе до `SIGTERM`; передай в `fail()` (или в место, откуда идёт retry) флаг, что воркспейс жив и есть WIP-коммит, чтобы следующий `runVariant` для этой задачи стартовал с `opts.resume = <session этого запуска>` и БЕЗ пересоздания worktree, а не с чистой базы. Session этого запуска бери из первой строки `stdout.log` (`type:"system", subtype:"init", session_id`), не из последней — на таймауте финальной строки `result` не будет.
Приёмка: селфтест-сценарий — фиктивный агент, который делает один коммит и зависает; демон убивает по таймауту (уменьши `timeout_min` для сценария через `conveyor.json`-подобный конфиг самотеста); следующая попытка стартует с `--resume` и НЕ создаёт новый пустой worktree (проверь, что `git log` во второй попытке содержит WIP-коммит первой). Существующие сценарии таймаута (если есть) не ломаются.

### 3.4 W1-4 · Возврат в очередь сбрасывает модель
Файл: `factory/daemon/conveyor.mjs`.
В блоке `nolSync`'а `existing`-ветки (раздел 2, строка ~435) добавь сброс модели рядом со сбросом `attempts`/`error`: `model = MODELS.includes(t.model) ? t.model : (repo.cfg.model || null)` — то есть либо явная модель с карточки, либо репо-пин, либо пусто (снова решит приёмщик). Не трогай логику `attempts = MAX(attempts-1,0)` при перезапуске демона (строка 2828) — она размышленно устроена так.
Приёмка: селфтест — карточка с `model='opus'` в базе демона, статус `failed`, board-карточка возвращена в `Queued`; после `nolSync` модель у задачи — репо-пин или пусто, не `opus`.

### 3.7 W1-7 · Хранилище без потолка
Файл: `assets/nol.js`.
Перепиши только `load()`/`persist()` для главной базы `db` (раздел 2) на IndexedDB с тем же синхронным по ощущениям API наружу — то есть `store.get/add/update/remove` остаются синхронными для вызывающего кода приложений (держи `db` в памяти как сейчас, но зеркаль на IndexedDB асинхронно в фоне при каждом `persist()`, и загружай из IndexedDB при старте вместо `localStorage.getItem`). Не трогай остальные ключи localStorage (язык, синк-конфиг, недавние результаты, kept/keep) — они маленькие и не растут. Добавь индикатор объёма базы на Главной (`apps/home.html` или где уместно) — просто примерный размер в КБ/МБ.
Приёмка: `node scripts/smoke.mjs` зелёный (там, где он проверяет приложения — база теперь читается из IndexedDB, страницы должны грузиться так же); ручной тест — 50 тысяч синтетических записей в CRM открываются без видимого подвисания (проверь на реальном прогоне, не только по коду); откат на localStorage не нужен, но если IndexedDB недоступна (приватный режим Safari иногда режет её) — тихий откат на текущее поведение с `localStorage`, не белый экран.
