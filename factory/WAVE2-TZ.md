# ТЗ «Волна 2: один продукт, а не сорок приложений» (эпика WAVE2)

Документ для агентов конвейера. Читай весь документ, потом только свой раздел 3.x. Источник: `factory/PLAN-2.md`, раздел 3. Если код разошёлся с этим текстом — код побеждает, расхождение опиши в журнале событием `build`.

## 0. Зачем

Волна 1 сделала завод надёжным. Сорок приложений при этом остаются сорока отдельными инструментами: сделка не знает про свой счёт, обращение не знает про свою задачу, у продукта нет ни ролей, ни единого способа быстро куда-то попасть, ни установки на телефон как приложения. Эта волна делает из каталога инструментов один продукт.

## 1. Инварианты

1. Один агент = один коммит.
2. `node --test`, `node scripts/build.mjs`, `node scripts/smoke.mjs` зелёные всегда; `node factory/daemon/selftest.mjs` — при правках демона (после волны 1 это настоящий гейт, не маскируется).
3. Правила `factory/CONVENTIONS.md`: `NOL.h`, `NOL.val` для пользовательских строк, полный русский словарь на каждую новую строку, никаких зависимостей и сборки, никаких сетевых запросов кроме существующего GitHub-синка.
4. NOL — локальный продукт без сервера: у него нет пароля и нет бэкенда, который бы его проверял. «Роли» в разделе 3.4 — это организационная договорённость и видимость в интерфейсе, а не защита от человека, у которого есть доступ к самому пространству (тот, у кого есть токен синка, технически может всё). Это ограничение существующей архитектуры, не баг этой волны — не выдавай роли за security-барьер нигде в интерфейсе.
5. Ничего не спрашивай владельца об этом документе. Вопрос — только о поведении продукта, которого здесь нет, или об удалении данных.
6. Карточки этой волны не пересекаются по файлам почти нигде — можно строить в любом порядке, кроме 3.4 (роли) перед 3.2 (журнал действий), потому что 3.2 использует поле «кто сделал», которое вводит 3.4. Иди по порядку 3.1 → 3.6, это самый безопасный путь.

## 2. Общее по коду (проверено 24.09, коммит 71caf20)

- `store` в `assets/nol.js` (строка 41): три точки, через которые проходит любое изменение записи — `add(c, o)`, `update(c, i, patch)`, `remove(c, i)`. Это единственное место, где можно без изменения сорока приложений повесить универсальный хук (для 3.2 и частично для 3.1).
- Межколлекционные ссылки сегодня: только `clientId`, `companyId` (в CRM/Deals). Остальные связи (найм → люди, обращение → задача) не выражены полями, только текстом.
- `notesPanel(coll, ref)` (строка 1436) — существующая панель заметок на карточке записи, используется везде. Это НЕ журнал действий: заметки пишет человек, а не система.
- `sync.cfg.user` (строка 429) — логин GitHub того, кто настроил синк в этом браузере. Это ближайшее к идентичности, что есть сегодня; единой системы пользователей и сессий нет.
- `searchDialog()` (строка 1796) — единственный намёк на быстрый переход, открывается по клику на «Search» в сайдбаре. Палитры команд с горячей клавишей нет.
- PWA: `manifest.json` и service worker в репозитории отсутствуют полностью.
- Демо-пространство (`assets/demo.js`, `?demo=1`) — используй как основу для проверки связей и ролей на скриншотах, не выдумывай новые демо-данные с нуля, расширяй существующие.

## 3. Карточки

### 3.1 W2-1 · Связи между приложениями
Файлы: `apps/deals.html`/`apps/crm.html` (сделка → счёт), `apps/hiring.html` + `apps/onboarding.html` + `apps/people.html` (найм → онбординг → люди), `apps/desk.html` + `apps/tasks.html` (обращение → задача). Закупка → склад уже связаны, использовать как образец паттерна (`assets/nol.js`, `poOpen`/`poLate`/`poTotals` и код Purchase Orders).
На карточке сделки, выигранной в статус «Closed Won»: кнопка «Create invoice» создаёт счёт с `dealId`, суммой из сделки, клиентом из `clientId`; на карточке счёта обратная ссылка на сделку. Оплата счёта пишет запись в Cash flow (`apps/cashflow.html`) автоматически, если счёт помечен оплаченным — свяжи через `paymentDate`/`status` счёта, не дублируй ручной ввод. На кандидате, нанятом в Hiring: кнопка «Start onboarding» создаёт план онбординга с `hireId`, по завершении плана — создаёт запись в People со ссылкой назад. На обращении в Desk: кнопка «Create task» создаёт задачу с `ticketId`, статус задачи виден на карточке обращения.
Приёмка: полный цикл на демо-данных — сделка → счёт → отметка «оплачен» → строка в денежном потоке, все три записи видят друг друга обратными ссылками; то же для найма и обращений. Существующие функции без связей (создание записи вручную без исходной) продолжают работать.

### 3.2 W2-2 · Журнал действий
Файл: `assets/nol.js` (новая коллекция и функция), новое приложение `apps/audit.html` только для владельца.
Добавь коллекцию `audit` рядом с существующими (`COLLS`). В `store.add/update/remove` (раздел 2) пиши в неё запись `{coll, ref, action: 'add'|'update'|'remove', who: sync.cfg?.user || 'local', ts: now(), fields: Object.keys(patch||{})}` — только имена изменённых полей, не значения (значения через `notesPanel`/саму запись, дублировать не нужно). Не пиши аудит для самой коллекции `audit` (бесконечный цикл) и для `notes` (уже есть своя видимость). Новое приложение показывает последние 200 записей журнала со ссылками на исходные карточки, фильтром по коллекции и по «кто».
Приёмка: изменение записи в CRM появляется в журнале за секунды с именем поля, ссылка ведёт на карточку; журнал переживает `?demo=1` (не пишет аудит на демо-данные, если это создаёт лишний шум — реши сам и опиши решение в журнале сборки).

### 3.3 W2-3 · «Прервать и сказать» — чат с работающим агентом по-настоящему
Файл: `factory/daemon/conveyor.mjs`, `apps/factory.html`.
Волна 1 (W1-3) научила демон делать WIP-коммит и возобновлять сессию при таймауте. Используй тот же путь для владельца: `POST /api/task/:id/say`, когда задача в статусе `running` (не только `asking/needs_review/failed`, как сейчас) — заставь текущий заход остановиться на безопасной точке (пошли `SIGTERM` тому же обработчиком, что и таймаут в W1-3, с тем же WIP-коммитом и captured session), и следующий запуск делай `resume` с добавленным текстом владельца как частью промпта продолжения. В `apps/factory.html` в пульте агента (`Agent console`, раздел 5.3 старого ZAVOD-TZ) верни форму чата и для статуса `running`, убери ограничение, которое поставила W1-5 (или её эквивалент — найди, где чат сейчас скрыт для running, и покажи снова, раз API это принимает).
Приёмка: селфтест — фиктивный долгий агент, `POST /api/task/:id/say` во время `running` останавливает его с WIP-коммитом и перезапускает с этим текстом в промпте; в интерфейсе форма чата видна и отправляется на карточках `running`.

### 3.4 W2-4 · Роли и организационная видимость
Файлы: `assets/nol.js` (новое поле у синка/пространства), `apps/people.html` (роль человека), везде, где полезно скрыть управляющие кнопки от не-владельца.
Добавь `sync.cfg.role` (owner/employee/guest), выбирается при подключении к пространству (владелец пространства — тот, кто его создал/импортировал первым, определяется по существующему `join`/`connect` потоку — прочти его в `sync.connect`/топбаре перед тем, как трогать). Owner видит всё. Employee не видит: удаление пространства, экспорт всей базы целиком, вкладку журнала действий других людей (видит только свой). Guest видит только то приложение, в которое его пригласили (минимально: CRM или Desk — выбери то, что реалистичнее для внешнего гостя, опиши выбор в журнале). Это видимость интерфейса (раздел 1, пункт 4), не защита данных.
Приёмка: три роли на демо-пространстве дают три разных набора видимых пунктов сайдбара и кнопок; смена роли обновляет интерфейс без перезагрузки.

### 3.5 W2-5 · PWA
Файлы: новый `manifest.json`, новый `sw.js`, правки `<head>` во всех `apps/*.html` и `index.html`.
`manifest.json`: имя «NOL», короткое имя, иконки (переиспользуй существующий SVG-фавикон из `apps/factory.html` как основу, сделай PNG 192/512 через простой генератор без зависимостей — canvas в браузере на этапе сборки, не npm-пакет), `display: standalone`, тема — акцентный цвет из `nol.css`. `sw.js`: кэш app-shell (сама страница, `nol.css`, `nol.js`, языковые файлы) для офлайн-открытия уже посещённых приложений; данные (`localStorage`/IndexedDB после W1-7) офлайн не трогает, они и так локальные. Регистрация service worker одной строкой в `nol.js`, не в каждом файле приложения.
Приёмка: `node scripts/smoke.mjs` зелёный; Lighthouse PWA-чеклист вручную (installable, manifest валиден) — опиши в отчёте тестировщика, если инструмента нет под рукой, хотя бы: `manifest.json` отдаётся с правильным content-type, `sw.js` регистрируется без ошибок в консоли на живом сайте.

### 3.6 W2-6 · Палитра команд
Файл: `assets/nol.js`.
⌘K (Ctrl+K на не-Mac) открывает палитру: создать запись любого типа («+ Contact», «+ Task», …, список типов из `COLLS`), перейти в любое приложение (список из `SECTIONS`), результаты существующего поиска (`searchDialog()` — либо расширь его до этого, либо построй палитру поверх той же функции поиска, не дублируй логику поиска). Esc закрывает, стрелки и Enter работают.
Приёмка: ⌘K из любого приложения открывает палитру за меньше секунды, создание записи из палитры работает так же, как через обычную форму, русские подписи на месте, 390px не ломается.

## 4. Проверка

Гейты как всегда: `node --test`, `node scripts/build.mjs`, `node scripts/smoke.mjs`; `node factory/daemon/selftest.mjs` для 3.3, если она правит демон. Критик смотрит дифф. Тестировщик проверяет прод после каждого мерджа; для правок только демона в 3.3 может пропустить проверку продукта, но обязан проверить `/api/task/:id/say` на живом демоне, раз это новое публичное поведение API.
